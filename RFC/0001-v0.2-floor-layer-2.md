# RFC 0001 -- v0.2 Floor: Layer 2 (Runtime Validation)

> The second blueprint. Floors the runtime-validation layer (Layer 2) with a minimum-viable implementation that complements the v0.1 typed-model floor.

## Status

In Review

## Champion

Emmanuel A. Otchere

## Date opened

2026-10-11

## Date closes

2026-10-25 (minimum 14 days from opening)

## Motivation

The discipline's four-layer stack was defined in the 2026 reframing essay and operationalised in `Source-Engineering/source-engineering-architecture/four-layer-stack.md`. The v0.1 blueprint (RFC-0000, captured implicitly in `Source-Engineering/source-engineering-architecture/blueprints/v0.1/`) floored Layer 1 (Typed Model) only. The other three layers were referenced but not floored.

v0.2 is the next-foundational floor. It is required because:

- **The discipline's hesitation factor is not fully closed at Layer 1.** A decision can be structurally valid (the answer fits the declared shape) and evidence-anchored (the evidence chain resolves) but still be wrong in a way the user cannot see. The hesitation factor closes at the layer that surfaces runtime signals: drift, segment-aware divergence, parameter-set out-of-range, temporal-validity drift. That layer is Layer 2.
- **The case study's first finding opened Q3.2** (recursive evidence chains) but the case study also surfaced a second-order issue: the COTS in the case study did not surface calibration drift. The discipline's most-valuable signal -- that a model's calibration has shifted on the user's segment -- is invisible without Layer 2.
- **Layer 1's conformance test cases (TC-L1-01..07) are not sufficient for production.** A COTS that passes TC-L1-01..07 is structurally valid; it is not yet a decision the user can trust at production latency. Layer 2 is what makes the decision trustworthy at production latency.

## Proposed change

v0.2 floors Layer 2 (Runtime Validation) with the following:

- **Layer 2 contract adoption.** The contract at `Source-Engineering/source-engineering-architecture/layer-contracts/layer-2-runtime-validation.md` becomes normative for v0.2-conformant implementations. Implementations that do not satisfy the contract are not v0.2-conformant.
- **Validation record schema.** A new field is added to the COTS schema: `cots.decisions[*].validation` (a `Validation` object that captures the ValidationFlags, the `decision_on_validation`, and the validation's runtime metadata). The schema is in `Source-Engineering/source-engineering-specifications/cots/README.md`; v0.2 is the version that adds the field.
- **Conformance test cases.** A new set of canonical test cases (TC-L2-01..N) is added to `Source-Engineering/source-engineering-specifications/compatibility-test-suite.md` and implemented in `Source-Engineering/source-engineering-conformance/`. The test cases cover the Layer 2 contract's guarantees.
- **Reference implementation.** The reference implementation in `Source-Engineering/source-engineering-reference-implementation/` adds a `Layer2` module that takes a Layer 1 DecisionRecord and the Context, runs the validation, and attaches the Validation record. The reference implementation's tests (currently 10/10) grow to cover the Layer 2 contract.
- **Tools.** The `se-trace` CLI in `Source-Engineering/source-engineering-tools/` adds a `se-trace validate-runtime` subcommand that surfaces the ValidationFlags to the user.
- **Practice.** A new chapter in `Source-Engineering/source-engineering-practice/handbook/` covers how a reviewer reads a Layer 2 Validation record.
- **Education.** A new section in `Source-Engineering/source-engineering-education/curriculum.md` (Unit 2.5 or a new Unit 6) covers Layer 2.

The change is backward-compatible at the COTS level: a v0.1 COTS is a v0.2 COTS with the new `validation` field absent. The v0.2 conformance suite treats the field as optional for v0.1 COTSs; a v0.2-conformant COTS must carry the field.

## Alternatives considered

- **Skip v0.2 and go directly to v1.0.** Rejected. The v0.1 floor is incomplete; the discipline is not yet shippable without Layer 2. A v1.0 that floors Layer 2 implicitly is harder to evolve than a v0.2 that floors Layer 2 explicitly.
- **Floor Layer 3 (Business Guardrails) before Layer 2.** Rejected. Layer 3 depends on Layer 2; the guardrail layer applies rules to a validated decision. A Layer 3 floor without a Layer 2 floor is a guardrail layer on top of an unvalidated decision.
- **Floor Layer 4 (Audit Trail) before Layer 2.** Rejected. Layer 4 depends on Layer 3; the audit trail records the guardrail's verdict. A Layer 4 floor without a Layer 3 floor is an audit trail of an un-guarded decision.
- **Floor Layer 2 with a different contract than the one already written.** Rejected. The contract at `Source-Engineering/source-engineering-architecture/layer-contracts/layer-2-runtime-validation.md` was the result of the 2026 reframing; departing from it would mean a separate discipline lineage.
- **Defer v0.2 until the case study's protocol is run.** Rejected. The case study is a real-protocol follow-on; the v0.2 floor is the discipline's engineering follow-on. The two are independent.

## Consequences

Easier:

- The discipline's hesitation factor is closed at the runtime-signal level. The user sees drift, segment-aware divergence, and parameter-set out-of-range in the COTS, not in a separate dashboard.
- The conformance suite grows to 12 + N test cases. The N test cases are the Layer 2 test cases; the discipline's gate is tighter.
- The reference implementation's Layer 2 module is the discipline's reference for "how do I implement runtime validation in a new framework". New frameworks can copy the pattern.
- The case study's second-order finding (calibration drift is invisible) is closed.

Harder:

- The COTS schema gains a new optional field. Implementations that do not yet support the field are not broken, but they are not v0.2-conformant.
- The conformance suite's runtime is longer (more test cases). The CI cost is higher.
- The reference implementation grows from 10 to 15-20 tests. The CI cost is higher.
- The tools' CLI gains a new subcommand. The documentation grows.

Commitments:

- The discipline commits to keeping Layer 2's contract at `Source-Engineering/source-engineering-architecture/layer-contracts/layer-2-runtime-validation.md`. Changes to the contract require an RFC.
- The discipline commits to the Layer 2 conformance test cases being normative. An implementation that fails any of them is not v0.2-conformant.
- The discipline commits to the Layer 2 reference implementation being the discipline's reference. Departures from the reference are allowed but must be justified.

## Migration path

The migration is sequenced:

1. **Stage 1 (week 1-2).** Add the `cots.decisions[*].validation` field to the COTS schema. The field is optional at v0.1; required at v0.2. Update `Source-Engineering/source-engineering-specifications/cots/README.md`.
2. **Stage 2 (week 3-4).** Author the Layer 2 conformance test cases (TC-L2-01..N). Land them in `Source-Engineering/source-engineering-specifications/compatibility-test-suite.md`. Implement them in `Source-Engineering/source-engineering-conformance/`. The conformance suite grows from 12 to 12 + N test cases.
3. **Stage 3 (week 5-7).** Implement Layer 2 in the reference implementation. Add the `Layer2` module. Update the examples to run the new layer. The reference implementation's tests grow from 10 to 15-20.
4. **Stage 4 (week 8).** Add the `se-trace validate-runtime` subcommand to the tools. Update the tools' documentation.
5. **Stage 5 (week 9-10).** Author the practice handbook chapter and the education curriculum section.
6. **Stage 6 (week 11-12).** Cut the v0.2 release. Tag the discipline's repos. Update the snapshot doc.

The migration is backward-compatible at the wire format: a v0.1 COTS is a v0.2 COTS with the new field absent. The conformance suite accepts v0.1 COTSs; the v0.2 conformance test cases only apply to v0.2-conformant COTSs.

## Open questions

- **How many Layer 2 test cases does v0.2 need?** The current proposal is 5-8 test cases. The discipline's review will set the number.
- **Does the COTS schema's `validation` field carry the Layer 2 validation, the Layer 3 guardrail decision, the Layer 4 audit entry, or all three?** The current proposal is the Layer 2 validation; the Layer 3 and Layer 4 fields are deferred to v0.3 and v0.4. The discipline's review may consolidate the fields into a single `cots.decisions[*].runtime` namespace.
- **Does the reference implementation's Layer 2 module ship with a calibration data source, or does it accept a pluggable calibration provider?** The current proposal is pluggable; the reference ships with a stub. The discipline's review may require a specific calibration source.
- **Does the `se-trace validate-runtime` subcommand run the Layer 2 conformance test cases, or does it run a separate runtime-validation set?** The current proposal is separate; the discipline's review may consolidate.

## Notes

This RFC is the second foundational change to the discipline, after the v0.1 floor (which was the discipline's first blueprint). The v0.2 floor is the natural next step in the discipline's evolution; the alternatives considered above are documented for the discipline's history.

The RFC's champion is the founding author. The RFC is open for review until 2026-10-25. The discipline's review is on the proposal's motivation, the proposed change, the alternatives considered, the consequences, the migration path, and the open questions.
